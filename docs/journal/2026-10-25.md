# 2026-10-25

## TASK-116 step 0 (P0 gate): what gt4-gs really answers in Performance mode

The rc6 plan gates both changes on one question (TASKS.md, "rc6 plan after the step 1 studies", step 3): in Performance
mode (`HWDownloadMode = 2`, NoReadbacks) does the GS process answer the 2 KiB flare readback with the same bytes as
Accurate (so a local answer would be byte-identical), with zeros (so the flares would be gone), or with older real pixels
(so a local answer is one frame late)? The owner's fact of 2026-10-24 — the street-light glows SHOW on George V in
Performance mode — already ruled out zeros; this probe answers the rest from a log.

**Probe.** `GT4_GS_READBACK_LOG=1` (new test switch, `native/gs_stream/gs_readback_probe.*`) prints one line per READ_FIFO
reply with the frame, guest destination, qwords, status, EE wait, nonzero byte count, the first 16 bytes, an FNV-1a 64
hash of the whole reply and whether the reply repeated the previous one for the same destination; at exit it prints one
row per destination (calls, distinct replies, repeats, zero replies, nonzero byte range, statuses, mean and max wait,
first and last hash). It also prints the `HWDownloadMode` of the ini named by `GT4_GS_CONFIG`, so a log says which mode
produced it. The probe only reads the reply after the client copied it: no record changes. `game_main.cpp` gives the
client the guest RAM window (`ps2::g_ram`), so destinations are EE addresses; the client itself stays donor-free.
`scripts/frame_cost_headless.py` gained `--readback accurate|no-readbacks` (writes `HWDownloadMode` 0 or 2, recorded in
`conditions.json`).

**Runs** (headless, 1x, surfaceless, gt4-gs 1.2.1 `887f5bf9…`, probe build `45c8c8df…`, 97,387,520 bytes, slice298;
`O:\gt4recomp-scratch\slice298-runs\`):

| Run | VBlanks | Readbacks | Flare destination | qwords | Calls | Distinct | Repeated | Zero replies |
|---|---|---|---|---|---|---|---|---|
| night Accurate | 16,000 | 5,026 | `0x01bf6f40` | 128 | 4,998 | 2,161 | 2,599 | 0 |
| night Performance | 16,000 | 5,026 | `0x01bf6f40` | 128 | 4,998 | 139 | 4,717 | 0 |
| day Accurate | 16,000 | 292 | `0x01bf6f40` | 128 | 264 | 52 | 129 | 0 |
| day Performance | 16,000 | 292 | `0x01bf6f40` | 128 | 264 | 6 | 258 | 0 |
| menus Accurate | 4,200 | 0 | - | - | - | - | - | - |
| menus Performance | 4,200 | 0 | - | - | - | - | - | - |

- **The per-frame night readback is the flare table** (Confirmed): one 128-qword reply per race frame to `0x01bf6f40`
  (the flare object of `RacePS2Base+0xDA0`), in a day race only while the sun is sampled (264 of 16,000 frames).
  `128` qwords is unique among every readback measured, so it is a safe allow-list key.
- **Performance mode does NOT answer zeros** (Confirmed): the night reply has 27..2048 nonzero bytes, never zero, and
  the glow shows, as the owner reported. The status field is 0 in every reply, including the ones that are all zeros:
  gt4-gs 1.2.1 never sets `kReadbackZeroFilled`, so the client's zero-filled counter cannot detect a blank reply.
- **The Performance reply is stale, not identical** (Confirmed by the counts, High confidence for the mechanism): the
  same buffer is read without waiting for the GPU, so distinct replies fall from 2,161 to 139 and repeats rise from
  2,599 to 4,717 of 4,998. The visibility table the game sees is therefore a *previous* frame's, sometimes several
  frames old, depending on GPU timing.
- **Verdict for step 1:** the local answer is **one frame late, not byte-identical**. That is not a regression: it is
  exactly what Performance mode already delivers today, only deterministic (the previous frame's accurate reply,
  independent of GPU timing) and cheaper (no 5.5 ms VU1 drain, no round-trip wait).
- **What actually breaks in Performance mode** (Confirmed): the one-shot readbacks. Car icons: the 256-qword replies
  become a constant 1024-byte pattern and the 768-qword ones lose their content (first reply all zeros); the loading
  picture (2 x 26,880 qwords) comes back all zeros. This matches the launcher's claim about the icons and contradicts
  its claim about the flares.
- **EE waits of the flare reply** (1x, mean/max): night Accurate 0.911 / 12.829 ms, night Performance 0.462 / 4.208 ms;
  day Accurate 0.639 / 1.490, day Performance 0.276 / 0.997. The 5.5 ms VU1 drain is separate (`mtvu download`) and is
  what step 1 removes.
- **Identity:** the same build with `GT4_GS_STREAM_HASH=1` gives the release 1.3.0 night hash `c091716e3cb40d79`
  (27,259,715 records), equal to the slice278/279 pin in docs/BUILD.md: the probe posts nothing new.

**Launcher help text corrected** (en-US and pt-BR, and `docs/launcher/gs-settings.toml`): Performance Mode now says the
game stops waiting for the images, so the car icons can come out blank and the loading picture may be missing, while
night flares still show but can be a frame behind. The old text said flares were skipped.

**Checks:** CTest 46/46 in the probe build (new `native_gs_readback_probe`: ini section/case/comments/range, FNV-1a 64
vectors, aggregation, environment switch); Python suite 697 tests OK, 43 skipped (`GT4_NATIVE_BUILD` = slice298);
`tests/python/test_frame_cost.py` covers the new `--readback` mapping.

**Not covered by this probe:** George V Paris in Spec II, photo mode and replays (they need menu navigation; the owner's
test build will log them with the same switch), and the Spec II executable (same client and runtime code path, but its
own build).

**Commit:** `1b4c8d3` on `task/116-117-flare-perf` (branch pushed). Step 1 (local answer with the previous reply, no VU1
drain) starts only after the owner sees this result.

## TASK-116 step 1: the flare readback without the drain (Performance mode)

**What changed.** `sync("download")` no longer drains the MTVU journal when the client answers the readback locally: it
closes the VIF1 batch and returns (counted as `download_deferred`). The client (`native/gs_stream/gs_stream_client.cpp`)
then copies the previous reply into the guest buffer and queues a new journal entry (`EntryKind::Readback`,
`GsSink::readback`, `EeJournal::append_readback`) so the READ_FIFO is posted at its stream position by
`Session::post_read_fifo_nowait` without waiting. The reply is collected one frame later by request id
(`Session::readback_reply`, exact id only: a reply replaced by a later request is not used). Only the 128-qword flare
table is local; every other readback drains on demand (`mtvu::drain_download`, F8 category `mtvu download`) and waits;
the first flare readback of a scene does the same, so the game never starts from a blank table. A GS hard reset clears
the cache. A/B switch `GT4_GS_READBACK_LOCAL=0`; the mode comes from `HWDownloadMode` in the ini named by
`GT4_GS_CONFIG` (Performance mode = 2). With the worker off (MTVU), in donor mode or without the ini the local answer is
not used. `scripts/external_runtime_probe.py` lists the switch, so owner runs never inherit it. New CTest coverage:
`native_gs_stream_ipc` (no-wait post + collect by id, a stale id refused), `native_mtvu_journal` (the readback entry keeps
its place between GIF outputs), `native_gs_stream_client` (two new scenarios with a pattern consumer: the first readback
waits, the second is the previous reply byte for byte, a 512-qword readback is never local and its request still lands
after the queued one — three requests, ids 1-3; and the kill switch keeps every reply fresh).

**Night race, headless 1x** (`O:\gt4recomp-scratch\slice298-runs\`; gt4-gs 1.2.1 `887f5bf9…`, build `45c8c8df…`+):

| Run | Blocking `download` syncs | Deferred | Readback wait total | Records | GIF records | Readbacks |
|---|---|---|---|---|---|---|
| Accurate | 5,026 | – | 4,596.6 ms | 27,259,715 | 27,143,620 | 5,026 |
| Performance, rc5 behaviour | 5,026 | – | 2,329.1 ms | 27,259,755 | 27,143,660 | 5,026 |
| **Performance, step 1** | **29** | 5,026 | **46.1 ms** | 27,259,755 | 27,143,660 | 5,026 |

- **The stream structure is exactly the one today's Performance mode produces** (same record count and the same GIF
  record count; the bytes differ only in the flare pixels, as they already do in Performance mode). The Accurate run with
  this build still hashes `c091716e3cb40d79` — the release 1.3.0 pin — so Performance mode off is byte-identical to rc5.
- **The flare reply** (`0x01bf6f40`, 128 qwords): 4,998 calls, 4,997 answered locally, 2 collected without a fresh reply
  (kept the older table), never zero, mean EE wait **1 us** (max 6.7 ms on the first, accurate one).
- **Where the 5.5 ms went:** the blocking drain's scope (`mtvu wait download`) contained both the wait for the worker and
  the EE's own work of writing the frame's GIF data to the GS ring. With the drain gone, `EE gs_drain` rises from 0.2-0.4
  to 2.2-4.2 ms/frame and the wait itself goes to ~0: the net EE saving in the race stretch is about 2-3.5 ms/frame, not
  the full 5.5 + 1.2. The owner's paced F8 decides what that buys on George V.
- **Other checks:** day race (292 readbacks, 263 local, 0 without a fresh reply), menus (0 readbacks), `GT4_MTVU=0` (local
  answer never engages; 28 readbacks served accurately), `GT4_MTVU_VERIFY=1` over 11,000 VBlanks: 11,000 frames compared,
  0 mismatches. CTest 46/46, Python 697 OK (43 skipped).

**Deviation from the plan.** The plan expected "GS stream hash unchanged". In Performance mode the hash cannot stay at the
Accurate value: the game draws its flares from the visibility table, so any Performance-mode answer (today's gt4-gs one or
ours) changes those pixels and the hash with them. What was verified instead: the record structure and every count are
identical to the pre-rc6 Performance-mode run, and the Accurate hash is unchanged.

## TASK-117: the flare-limits ELF is built, and its identity gate failed (NOT in rc6)

**Built.** `scripts/flare_limits_elf_patch.py` (own MIPS assembler, pinned table, `check` / `verify` / `produce` /
`record-library`) derives `SCUS_973.28.flare.elf` (sha256 `6c156b5f…`) from the pinned reconstructed ELF: the TASK-080 P2
rows, the four `jal` redirects (0x3B7BE4 and 0x3B85C0 to the track/car helpers at 0x4955A0 / 0x495600, 0x3B8BA0 and
0x3B8CE8 to the halo helper at 0x495580) and 49 helper words in the zero padding. Each helper reads the block at 0x7F10,
and with flags 0 jumps to the original routine with `ra` untouched (call + 8, delay slot unchanged); it only touches
caller-saved registers (t0-t2, $f0; $f19 for the halo, loaded right before each call and never read after it). The
generated code calls the helpers from unit_00AD (track fill) and unit_00AE (car fill and both halos), and unit_00E5 holds
the three new entries (91-93) with unit_00E6 keeping the flare routine. Translation used the accepted seed set unchanged;
the translator reports 138,815 entries against 138,813 for the original. Eight units differ from the slice208 library
(008E, 008F, 00A6, 00A7 for the TASK-080 rows and the entry-id renumbering, and 00AD, 00AE, 00E5, 00E6 for the redirects).
The library is pinned in `docs/inputs/slice299-ee-libraries.json` (profile `flare`, sha256 `d322b0aa…`, 327 objects) and
CMake has the `flare` profile. `native/flare_limits.*` writes the six-word block (flags 7, 60, 40, caps 12/12) whenever
`GT4_FLARE_LIMITS=1` and never touches memory when the switch is off (verified: the game does not write 0x7F10 either).
CTest `native_flare_limits` and `tests/python/test_flare_limits_elf_patch.py` pin every word, the redirects and the block
offsets.

**Why it is not shipped.** The identity gate failed. With the switch off (the v2.00 flare build, night race, Accurate
readbacks), the frame dumps are identical to the rc5/aspect build up to frame 9000 and differ from frame 10000, the first
one after the flares appear, and the GS stream diverges: 27,246,609 records and hash `4cf0652c…` against 27,259,715 and
`c091716e…` for the aspect build (which is stable across runs). A 1,600-frame capture of the menus is byte-identical
between the two builds, so the divergence starts with the flare code, and it is a behaviour difference, not a chunking
difference (13,106 fewer GIF records and 3 fewer flare readbacks in the night run). The inert path was checked: flags 0
reaches the original routine with the same registers, the block is never written, and the call structure (a cross-unit
call with the original return address) matches what the translator already emits for the same sites. The remaining
suspects are the extra guest instructions of a redirect (budget/preempt cadence) and the entry renumbering in unit_00E5.
The switch, the launcher variable and the flare library are therefore **not wired into the rc6 build**: the v2.00
candidate keeps the `aspect` library and the launcher sends nothing, so rc6 ships TASK-116 step 1 only. The launcher and
standalone changes were reverted with the rest of the rc6 wiring left for the fix; the ELF script, the pin and the host
module stay on the branch.

**Next step for TASK-117.** Find the divergence with a bisect: (1) a derived ELF with only the four redirects and a
4-instruction helper that jumps straight back (`j original`) — no load, no test — to separate "extra instructions" from
"new code"; (2) if that matches, add the load and the test back one step at a time; (3) in parallel, dump the entry tables
of unit_00E5 for both generations and check every caller of ids >= 91; (4) then re-run the gate (dumps and stream hash).

## Owner test of the step-1 portable build (1.3.0-rc6, 2026-10-25)

- **Performance mode off (Accurate), v2.00 and Spec II:** same behaviour as rc5, as designed (the step-1 code is inert).
- **Performance mode on:** George V Paris in Spec II ran at **60 FPS from start to finish**, no other lighting artefacts;
  the v2.00 night race was already at 60 FPS before the change. A few lag spikes at the start of each build, only on the
  first run, from shader compilation of a fresh cache.
- **One artefact, expected from the design:** in the night race, an opponent that brakes just before passing behind a wall
  keeps the **left** light's flare drawn **over the wall for one frame** (the right one is already hidden). The table is an
  occlusion result answered one frame late, so a light that becomes hidden this frame still shows last frame's value. Visual
  only; the EE never reads the table. Recorded in ai-memory `gotchas/flare-readback-one-frame-lag`; it must appear in the
  rc6 launcher note ("the night lights can lag a frame"), and TASK-117 (no halo, distance cull, caps) would hide most of it
  because far and haloed lights stop being drawn.
- **Numbers (his F8, 3440x1440, 21.5:9, Spec II George V at 6x; from `data\sessions\*\game.log` of the portable copy):**

  | Run | EE critical path | of 16.68 ms | `mtvu download` | readback wait (total) |
  |---|---|---|---|---|
  | v2.00 night, Accurate | 10.50 ms | 63% | 3.36 ms | 15,423 ms |
  | Spec II George V, Accurate | **18.36 ms** | **110%** | 5.43 ms | 32,352 ms |
  | v2.00 night, Performance mode | **5.91 ms** | 35% | **0.000 ms** | **46 ms** |
  | Spec II George V, Performance mode | **7.87 ms** | 47% | **0.000 ms** | **31 ms** |

  Local answers: 4,824 of 4,853 readbacks (8 without a fresh reply) in the v2.00 run and 5,497 of 5,512 (242 without) in
  the Spec II run. The heavy case (Spec II George V) went from over budget at 18.36 ms to 7.87 ms, which is the 60 FPS he
  saw from start to finish.
