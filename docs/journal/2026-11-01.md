## TASK-082: native variable frame rate & CoreGS 2.0 resumption roadmap

- Authored comprehensive architecture and resumption roadmap: [`docs/TASK-082-COREGS2-RESUMPTION-ROADMAP.md`](../TASK-082-COREGS2-RESUMPTION-ROADMAP.md).
- Diagnosed root cause of the visual defect observed during experimental testing of `rc7-test082` on an Intel Core i5-7200U laptop (Intel HD Graphics 620):
  - In GT4's main loop (`func_001016E8`), the guest engine alternates its double buffer index (`0x001077F8`, `D_006184C0.cur = 1 - cur`) and calls guest flip `func_00107878`, which writes the privileged `DISPFB2` register specifying which VRAM buffer is displayed.
  - On skipped frames, the simulation advances, but 3D rendering to VRAM is bypassed. However, the guest flip unconditionally inverts `cur`, directing the external GSdx process (`gt4-gs.exe`) to display an unrendered VRAM page containing stale visual content from seconds earlier (e.g. HUD timer `0:00.983` flashing during `0:06.433` and `0:10.016`).
  - Attempting to fix this across the legacy multi-process IPC stream is fragile and introduces synchronization stalls.
- Established CoreGS 2.0 in-process resumption architecture:
  - In CoreGS 2.0 (Phase 2), the renderer runs in-process with direct Vulkan swapchain control.
  - On skipped frames, `vkQueuePresentKHR` is suppressed and the display hardware holds the previous swapchain image (`present hold`).
  - The host frame scheduler intercepts `DISPFB2` writes, pinning the active display buffer pointer until the next fully rendered frame.
  - Flare readbacks (`download sync`) are decoupled on skipped frames, reusing previous intensity values to eliminate the 4.2 ms stall.
  - Outlined decoupled auxiliary frame passes (`AUX_FRAME`) for 120 Hz / 144 Hz presentation with fixed 60 Hz physics simulation.
- Retained experimental work safely preserved on branch `task/082-render-skip` at commit `15b7bf3` (PR #113 Draft) for CoreGS 2.0 resumption.
